# Telegram Mini App direct links

ROXY uses the Telegram **Main Mini App** configured for the bot. Public share,
repeat, profile, referral and prompt links are generated by
`app.services.feed_links.mini_app_deep_link`:

```text
https://t.me/<bot_username>?startapp=<payload>
```

The bot username comes from the existing runtime settings and Telegram bot
identity. Do not hardcode a bot name or append a guessed `/app` path. A named Mini
App short name is not required by this Main Mini App link contract. Legacy
`https://t.me/<bot_username>?start=<payload>` links remain supported by the bot,
which preserves the launch payload in its WebApp button.

## Ordinary referral entry

An ordinary `ref_<telegram_id>` launch opens the existing Home screen with current
trends, including legacy launcher URLs carrying `route=catalog`. The original
Telegram-signed payload remains available to the existing authenticated request
headers and server-side attribution. Client URL values never authorize a referral
reassignment. Deliberate navigation to history and other screens is not overridden
by Telegram's sticky `start_param`; content-specific share links retain their own
existing destinations.

The introductory tour is deferred for referral discovery, not automatically
completed. Protected actions still enforce server-owned onboarding and redirect
to `onboarding=1` on HTTP 428. That explicit gate always takes precedence.

## Connecting the Telegram chat

Opening a Mini App does not by itself grant permission to send private messages.
After the existing authenticated `/api/v1/me` request succeeds, Home offers
**Подключить чат Telegram**. A user click invokes Telegram's native
`requestWriteAccess` consent dialog (Telegram WebApp API 6.9+). No automatic popup,
automatic redirect or user-preference change occurs. Refusing permission does not
block browsing, and generated work remains available in the application history.

The signed `allows_write_to_pm` UI hint and a per-user session-only success flag
suppress redundant prompts. They are not accepted by a privileged backend API as
proof of access. Unsupported clients, SDK exceptions and a missing callback show
a manual chat fallback. Its URL is supplied by `/me.bot_chat_link` using the
existing configured bot identity. The user opens that chat and presses Start.

The `write_access_allowed` Telegram service message is handled before stateful
admin/customer handlers. It never creates a user, consumes first-touch referral
attribution or clears an unfinished FSM. A matching private chat can acknowledge
consent and recover the user's previously deferred transactional deliveries.
Messages in groups or from a mismatched private identity do not prove private
chat reachability. Existing notification preferences, outbox locks and retry
rules remain authoritative; Telegram's first send still has its existing
non-idempotent network/commit ambiguity.

## Verification and rollout

Browser coverage includes first referral landing, actual mobile trend content,
signed header retention, consent/grant/denial, timeout/late callback, duplicate
clicks, unavailable storage, old clients, unauthenticated entry, reload and the
mandatory onboarding boundary. The referral suites run in Chromium and the
explicit mobile WebKit CI matrix. Backend tests cover configured chat links,
private-only recovery, consent/FSM preservation and the unchanged welcome copy.

No schema migration, provider routing, wallet, tariff, promo or referral-economic
change is required. Release through the existing exact-SHA CI/deploy workflow;
rollback is a normal code revert without rewriting users or financial records.
Native Telegram consent is simulated in automated browser tests; a physical
Telegram client check is a separate verification, not implied by browser success.

Official contracts: https://core.telegram.org/bots/webapps and
https://core.telegram.org/bots/api#writeaccessallowed.
