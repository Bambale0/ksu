# Nano Banana slow-upstream incident - 2026-10-02

## Baseline and confirmed evidence

Audit baseline: `128f0a7f861a365c0d53d90b95104a7afda888c8` (main).
Production application image during diagnosis: `03280a6067b070137ad6ea29b8babefeedbcd223`.
No production prompt, image URL, credential, or customer identity belongs in this report.

KSU sends valid, normally JSON-serialized Nano Banana Pro requests. Multiple
requests, including a nine-character prompt, received Neironych HTTP 503
`submission_outcome_unknown` after approximately 126 seconds. Correlated logs
on the actual Neironych deployment show ArgoLink HTTP 524 at the same times.
This is an upstream synchronous-response timeout, not evidence of a JSON
escaping error or a crashed KSU worker. The upstream configured request timeout
is independently longer; increasing only KSU's timeout cannot undo an HTTP 524.

The published Neironych contract does NOT replay synchronous image results:
repeating the same idempotency key returns 409, not the lost image. A new key
can create another paid operation. Never turn an uncertain image into an
automatic new-provider attempt or reconstruct its original request body.

KSU's currently configured circuit requires five failures within 60 seconds.
Sequential image failures approximately 126 seconds apart cannot trip it.
The existing provider-wide success counter also allows a successful video to
clear image failures. These are separate, local resilience defects.

2. Reproduce the slow-failure/cross-model reset defects with deterministic
   regression tests before changing production code.

   policies. A scoped circuit must never bypass `_submission_uncertain` guards.
4. Verify sequential failures, another model's success, expiry/cooldown,
   disabled protection, Redis failure policy, and unchanged legacy circuits.

6. Release only a verified commit; distinguish containment from remediation
